233–240 行之间，某次漏掉的行（不在切口附近）在下一次运行里都被读到，单独识别它所在的那一段也能读到，所以不是分段造成的。

## 检查过、不算问题的

- JPEG 保存带透明背景的窗口截图：`NSBitmapImageRep` 会把透明像素压成白色，不会变黑（已验证）。
- Google 翻译表单编码：`&`、`=`、`+` 都被正确转义（已验证）。
- 拖动预览卡片生成的临时 PNG（`$TMPDIR/Shocrot/`）不会主动删除：系统会定期清理 `$TMPDIR` 里 3 天没用过的文件；
  如果在预览关闭时就删，拖进邮件等延迟读取文件的应用时可能读不到，所以保持现状。

## 剩余问题

1. **超宽截图的 OCR**：5K / 6K 显示器全屏截图（5120×2880、6016×3384）里只有中间一栏正文时，渲染的测试页
   Vision 一行都认不出；缩小到 2400 宽再识别也只能认出约一半。本机是内建屏（3024×1964 级别，实测正常），
   没法用真实 5K 屏幕确认，合成图可能夸大了问题（同样的合成方式在 1600×1600 的稀疏单栏图上也会失败，
   而真实界面文字分布更密）。建议有 5K/6K 外接屏时用真实截图复测；若属实，可在宽度方向也分块（需要处理被切开的行）。
2. **宽且高的滚动截图**（宽 > 3000 px，例如 5K 屏上的整窗滚动截图）分段后每段仍然很宽，可能同样受上一条影响，未验证。
3. 高图分段识别是串行的，30000 px 约 8 秒。可以考虑并行处理各段，但要先确认 Vision 并发时的内存占用。
4. Vision 偶尔会有一次约 60 秒的卡顿（模型冷启动 / 编译），和这次改动无关，修改前也出现过；首次识别慢的问题
   已有 `warmUp`，这个更长的卡顿原因未查。
