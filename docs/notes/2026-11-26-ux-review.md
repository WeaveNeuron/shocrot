## 1. Settings Sometimes Fails to Open

### Root Causes Found

1. **Silent activation failure on LSUIElement menu-bar apps**: `NSApp.activate()` (cooperative activation) can silently fail when another regular app holds foreground focus without yielding activation, leaving Shocrot's Settings window either behind other windows or inactive (reproduced live: `before_settings_open.png` showed Settings opening at `(959, 30)` behind another app with grey inactive traffic lights).
2. **Status-menu unwind focus race**: Clicking `Settings…` from an `NSStatusItem` menu can hand focus back to the previously frontmost regular app on the next run-loop turn after menu tracking unwinds.
3. **Cross-Space & minimized gaps**: `SettingsWindow` did not set `.moveToActiveSpace`, did not `orderOut` before re-presenting from another Space, and did not deminiaturize before ordering front.
4. **Misplaced initial frame**: `SettingsWindow` called `w.center()` before SwiftUI layout settled, positioning the window near the top-right `(959, 30)` instead of centered on the active display.
5. **Finder/Spotlight reopen bug (`applicationShouldHandleReopen`)**: Checking `if !flag` returned early whenever any floating panel (such as a hidden or visible `TranslatePanel`) or off-Space window existed, so reopening Shocrot from Finder/Spotlight failed to surface Settings.
6. **`⌘,` shortcut leak from floating panels**: `TranslatePanel` and `PinWindow` are non-activating floating panels; pressing `⌘,` while they were focused fell through to the underlying regular app (reproduced live: opened TextEdit's own Settings window instead of Shocrot's).
7. **Floating panel occlusion**: Clicking "Open Settings" from `TranslateView`'s `noServiceCard` or `ErrorRow` did not close an unpinned floating `TranslatePanel`, leaving the level-3 floating panel covering Settings.
8. **English sidebar truncation**: `NavigationSplitView` inside a fixed non-resizable `NSHostingController` window collapsed the sidebar column to `144 pt` (`~19.5%` of `740 pt`), truncating `"Text Recognition"` to `"Text Recog..."` (`before_settings_open.png`).

### Fixes Implemented

- Added `Sources/Shocrot/Common/WindowPresentation.swift` providing unified presentation (`activateApp()`, `prepare()`, `present()`, `centeredFrame()`, `shouldRelocateToActiveSpace()`, `reopenAction()`):
  - Unhides the app, deminiaturizes minimized windows, moves windows across Spaces cleanly (`.moveToActiveSpace` + `orderOut` before re-order when off-Space), centers hidden windows on the active mouse display using `preferredSize`, clamps on screen via `OnScreenKeeper`, activates with `.activateIgnoringOtherApps`, and re-asserts key/front on the next run-loop tick to beat the `NSStatusItem` unwind race.
- Applied `WindowPresentation` consistently across `SettingsWindow`, `HistoryWindow`, `OnboardingWindow`, `OCRWindow`, `AppController.showAbout`, and `AppController.recognizeFile`.
- Fixed `applicationShouldHandleReopen` in `Sources/Shocrot/App/main.swift` to surface visible/minimized main windows or open `SettingsWindow` even when floating panels exist.
- Intercepted `⌘,` inside `TranslatePanel.performKeyEquivalent` and `PinWindow.keyDown`, and unified `TranslateView.openSettings()` so unpinned panels close before presenting Settings.
- Replaced `SettingsView`'s collapsed `NavigationSplitView` with a fixed `212 pt` native `.listStyle(.sidebar)` column (`HStack` + `Divider()`), eliminating the `144 pt` collapse so `"Text Recognition"` displays completely untruncated.

## 2. First OCR Latency Optimization

### Root Causes Found

1. **Inadequate Vision warm-up**: The previous `OCRService.warmUp()` rendered a `256×64` single mixed line (`"Shocrot 截图"`), triggering 2× upscaling and warming only a single automatic-detection path. The first real bilingual capture still paid a **315.8–389.2 ms** cold penalty (~4.2× slower than the **82.1 ms** warm steady state).
2. **Launch-time work & contention**: Warm-up started immediately during launch without deferring past initial menu-bar setup or cancelling when a user triggered OCR immediately.
3. **Uncached Apple Translate availability**: `AppleTranslationService` called `LanguageAvailability().status(from:to:)` on every translation (~2.5 ms cold) and did not pre-warm `NLLanguageRecognizer` or availability status.
4. **Unnecessary barcode detection in Screenshot Translate**: `VNDetectBarcodesRequest` ran during `AppController.translate(image:)`, where barcode results are never used.
5. **No slow-first-run feedback**: On a brand-new binary (or after macOS updates), macOS compiles Vision/ANE assets once (~23.5–24.2 s one-time per binary); the UI previously gave no hint when OCR took longer than a second.

### Fixes Implemented

- Added `Sources/Shocrot/Common/PerfLog.swift` (`os.Logger` + `OSSignposter`) recording durations and counts only (never user text).
- Upgraded `OCRService.warmUp(delay:)` to defer `0.4 s` after launch, render a `640×200` multi-line bilingual image (`warmUpImage(for:)`, no upscaling), cache `supportedLanguages`, expose `isWarmingUp`, and cancel pending warm-up immediately if real OCR arrives (`cancelPendingWarmUp()`). Re-warms automatically when `Settings.ocrLanguages` changes.
- Added `detectBarcodes: Bool = true` to `OCRService.recognize` and passed `detectBarcodes: false` from `AppController.translate(image:)`.
- Added `AppleTranslationService.warmUp(primary:secondary:)` (warms `NLLanguageRecognizer` and caches `.installed` language pairs only; cache invalidated after `prepareTranslation()`).
- Added a subtle 1.2 s slow-first-run progress hint (`ocr.warmingUp`) in both `OCRWindow` and `TranslateModel` / `TranslateView`.

## 3. Screenshot Translation Panel Size Stability

### Root Causes Found

1. **Three-stage vertical jump (`176 → 338 → 463 pt`)**: Opening `TranslatePanel` via screenshot translate initially rendered a single `Recognizing text...` line (`inputHeight = minInputHeight`) and completely omitted the results `ScrollView` (`model.entries.isEmpty`), giving `420×176 pt`. Once OCR returned, the input expanded (`338 pt`), then results appeared and expanded again (`463 pt`) — a **+287 pt** layout jump (`before_translate_recognizing.png` → `before_translate_loaded.png`).
2. **Stale language chip during recognition**: `resolvedTarget` was not cleared when starting a new recognition or clearing text, flashing the previous session's target language chip while recognizing (`before_translate_recognizing.png`).
3. **Stuck hover state on header buttons**: Closing the panel while the pointer hovered the gear/pin button left SwiftUI `@State hovering = true` stuck when the reused panel reappeared (`before_translate_recognizing.png`).
4. **Zombie reopen after cancel**: Dismissing the panel during OCR did not cancel the in-flight `translateOCRTask`, allowing the panel to pop back open when OCR finished.

### Fixes Implemented

- Added selection-aware size estimation in `TranslatePanel` (`estimatedInputHeight(forSelection:)` and `estimatedResultTextHeight(forInputHeight:serviceCount:)`) so the panel opens near its final height on frame 1.
- Updated `TranslateModel.beginRecognizing(selectionSize:)` to pre-populate enabled service placeholder entries immediately and reset `resolvedTarget = nil` (also cleared in `clear()` and empty `translate()`).
- Updated `TranslateView` to render `SkeletonLines` placeholders inside both the input card and service result cards from frame 1 (no structural `ScrollView` insertion pop-in) with `.animation(.smooth(duration: 0.2), ...)`.
- Reset `IconButton.hovering` on `.onDisappear` and `.translatePanelWillClose`.
- Wired `TranslatePanel.onCancelRecognizing` to cancel `AppController.translateOCRTask` when dismissed mid-OCR.

### Live Verification

- **Height trajectory on identical TextEdit capture**:
  - Before: **`176 pt → 338 pt → 463 pt`** (+287 pt jump)
  - After: **`459 pt → 463 pt`** (**+4 pt total delta**)
- **PR #2 invariants verified live**:
  - Appears directly below selection (`x: 412, y: 360`)
  - Dragging header into menu bar (`y = 4`, `x + 50`): X preserved (`412 → 462`), Y clamped cleanly below menu bar (`y = 38`)

## 4. 划词翻译 (Selection Translation)

### Root Cause of Previous Failure

1. **Missing Accessibility permission** on the test machine left `AXIsProcessTrusted()` false.
2. **Brittle selection reader & clipboard side-effects**: The legacy `SelectionReader` only inspected `kAXSelectedTextAttribute` on the system-wide focused element and fell back to synthesizing `⌘C` via `CGEvent`, mutating the user's clipboard (`NSPasteboard`) and failing on Safari/WebKit static text and non-focused text surfaces.
3. **No direct mouse-selection workflow**: Users could only invoke selection translation via `⌥⇧D`, which opened the full source+target `TranslatePanel`.

### New Design & Implementation (`Sources/Shocrot/Translate/SelectionTranslate.swift`)

- **Mouse-release–following Liquid Glass trigger icon**:
  - Passive, event-driven global mouse listener (`NSEvent.addGlobalMonitorForEvents(matching: [.leftMouseDown, .leftMouseUp])`, zero polling) — always active whenever Accessibility permission is granted (`AXSelectionReader.isTrusted`). Dismiss monitors (`.rightMouseDown`, `.scrollWheel`, `.keyDown`, `didActivateApplicationNotification`) are installed only while the icon or popover is visible and torn down immediately on dismiss.
  - Triggers on drag selection (distance ≥ `6 pt`) or double/triple-click selection, ignored during active screenshot/scroll/recording sessions or cross-app drags.
  - Places a compact `30×30` non-activating Liquid Glass circular icon (`NonActivatingPanel`, `canBecomeKey = false`) directly at the **`mouseUp` release side**:
    - **Left → Right drag** (`mouseUp.x > mouseDown.x`): icon appears at the **end (right side)** of the selection.
    - **Right → Left drag** (`mouseUp.x < mouseDown.x`): icon appears at the **start (left side)** of the selection.
    - Vertically anchored to the AX selection line bounds when available (never covering the highlighted text), clamped inside the display under the pointer (multi-display & Retina aware via `SelectionPopupLayout.cgRectToAppKit`).
  - Auto-dismisses after `4.5 s` (paused while hovered via `SelectionAutoDismiss`), and dismisses immediately on `Esc`, outside click, scroll, typing, or app switch.
- **Minimalist Liquid Glass translation-only popover**:
  - Clicking the icon opens a `320 pt` non-activating Liquid Glass popover anchored near `mouseUp` (below preferred, flipping above if near the bottom edge, clamped on screen).
  - **Displays translation only (no source text box)**, with muted target-language caption and compact icon actions (Read Aloud, Copy Translation, Open in full `TranslatePanel`, Close `Esc`), plus inline offline language-pack download recovery if needed.
- **Pure Accessibility API & Privacy/Security Guarantees**:
  - `AXSelectionReader` cascades purely through macOS Accessibility attributes on both the focused element and the element hit-tested at the `mouseUp` screen coordinate:
    1. `kAXSelectedTextAttribute`
    2. `kAXSelectedTextRangeAttribute` + `kAXStringForRangeParameterizedAttribute`
    3. `kAXValueAttribute` sliced by `AXSelectedTextRange`
    4. WebKit `AXSelectedTextMarkerRange` + `AXStringForTextMarkerRange`
  - Selection line bounds read via `AXBoundsForRange` / `AXBoundsForTextMarkerRange`.
  - **Never synthesizes `⌘C` and never reads or writes `NSPasteboard`** (legacy `viaCopy()` removed from `TextHelpers.swift`). Silently does nothing when an app does not expose AX selection.
  - **Password & Secure Input suppression**: `SelectionSecurity.isProtected(...)` checks role/subrole/description (`AXSecureTextField` / password indicators) across a 4-level ancestor walk, plus `IsSecureEventInputEnabled()` via Carbon HIToolbox — never reads or shows an icon in password fields or secure input contexts.
- **Shortcut & Settings Decision**:
  - **Kept `⌥⇧D` (`Translate Selection`)** as a keyboard fallback, now routed through the pure-AX reader (never touches clipboard; shows a non-destructive Accessibility guidance banner if untrusted).
  - **No extra Settings toggle**: behavior is fixed — whenever Accessibility permission is granted, selecting text always reveals the floating translate icon (verified in `screens/after_settings_no_toggle.png`).

## Round 2

Follow-up polish on three selection-translation UX issues verified live on build 130 (`HEAD 6bd0c9d` → `fix/ux-review`), without adding any Settings toggles.

### 1. Selection Trigger Icon Obscuring the Next Line of Text

- **Root Cause**:
  1. `SelectionPopupLayout.iconFrame` unconditionally placed the `30×30` circular icon `6 pt` **below** `lineBand.minY` (`belowY = band.minY - iconGap - size.height`), dropping it directly over lines 2–3 underneath the selected text (`after_selection_textedit_lr_icon.png`, `after_selection_textedit_rl_icon.png`).
  2. `AXSelectionReader` previously read only the selected-range bounds (`AXBoundsForRange` / `AXBoundsForTextMarkerRange`), not the full visual line bounds, so placing the icon inline beside a mid-line selection would cover adjacent words on the same line.
  3. On WebKit (Safari), querying non-existent parameterized attributes (`AXStartTextMarkerForTextMarkerRange` / `AXEndTextMarkerForTextMarkerRange`) returned `nil`; WebKit exposes `AXTextMarkerRange` endpoints through the C API `AXTextMarkerRangeCopyStartMarker` / `AXTextMarkerRangeCopyEndMarker` paired with `AXLeftLineTextMarkerRangeForTextMarker` / `AXRightLineTextMarkerRangeForTextMarker`.
- **Fix**:
  - Upgraded `AXSelectionReader` (`Sources/Shocrot/Translate/SelectionTranslate.swift`) to resolve the full visual line containing the drag release endpoint:
    - **Cocoa (`AXTextArea` / `AXTextField`)**: uses `AXLineForIndex` + `AXRangeForLine` + `AXBoundsForRange` with a pure UTF-16 whitespace/newline trimmer (`SelectionPopupLayout.trimmedLineRange`) so trailing newlines never spill bounds onto the next line.
    - **WebKit (Safari)**: uses `AXTextMarkerRangeCopyStartMarker` / `AXTextMarkerRangeCopyEndMarker` with `AXLeftLineTextMarkerRangeForTextMarker` / `AXRightLineTextMarkerRangeForTextMarker` (falling back to `AXLineTextMarkerRangeForTextMarker`) and `AXBoundsForTextMarkerRange`.
    - **Adjacent-line & viewport clearance (`SelectionPopupLayout.clearedLineBounds`)**: expands the horizontal line edge past slightly wider wrapped neighbor lines (within `160 pt`) that vertically intersect the centered icon's span, and clips to enclosing `AXScrollArea` / `AXWebArea` bounds for horizontally scrolled content.
    - **Owning window containment (`AXWindow` + `SelectionPopupLayout.effectiveIconBounds`)**: reads the target element's owning `AXWindow` frame (`kAXWindowAttribute` → ancestor walk → `kAXFocusedWindowAttribute`) and intersects its `4 pt`-inset frame with the display's `visibleFrame`, ensuring the trigger icon stays strictly inside the target window and never spills onto neighboring apps in either direction.
  - Updated `SelectionPopupLayout.iconFrame` (`28×28` icon, `8 pt` horizontal gap):
    - **Left → Right** (or multi-click / downward multi-line): placed to the **right** of the selection's line (`line.maxX + 8`), vertically centered on that line (`midY ≈ line.midY`), when it fits inside the owning window's visible bounds.
    - **Right → Left** (or upward multi-line): placed to the **left** of the selection's line (`line.minX - 8 - 28`), vertically centered on that line, when it fits inside the owning window's visible bounds.

### 2. Translation Popover Readability & Label Contrast

- **Root Cause**:
  1. `SelectionPopoverView` applied `.glassEffect(.regular.tint(Color(nsColor: .windowBackgroundColor).opacity(0.76)))` directly without an opaque backing layer; Liquid Glass modulates tint alpha so high-contrast body text directly behind the popover bled through as distracting bright/dark blotches.
  2. The target language caption used `.foregroundStyle(.tertiary)` at `11 pt` regular, producing very low contrast against the translucent backdrop.
- **Fix**:
  - Layered a `ZStack` of `.thickMaterial` plus an appearance-adaptive high-opacity surface backing (`Color(white: 0.165).opacity(0.90)` in Dark mode for clear elevation over `#1e1e1e` editors; `Color(white: 0.985).opacity(0.93)` in Light mode) beneath `.glassEffect(.regular, in: shape)` and a subtle directional hairline stroke (`0.75 pt`), eliminating text bleed-through while preserving macOS 26 depth. Applied matching high-contrast frosted backing to `SelectionTriggerView`.
  - Upgraded the target language label from `.tertiary` (`11 pt`) to `Color(nsColor: .secondaryLabelColor)` at `11.5 pt` medium, and aligned body text (`.labelColor`) and popover icon buttons (`.secondaryLabelColor`, `.labelColor` on hover) to active system label contrast.

### 3. Localized Language Names Following the UI Language

- **Root Cause**:
  1. **Why Studio displayed `"Chinese (Simplified)"` on build 130**: On the Studio test host, `NSGlobalDomain AppleLanguages` is `("en-US")` and `com.weaveneuron.shocrot` had no `appLanguage` override (backed up to `backup-r2/com.weaveneuron.shocrot.plist`), so Shocrot was running in **English UI** (`L10n.language == "en"`). In `SelectionPopoverView`, translating English text into Chinese shows only the Chinese translation plus `target.name` (`L("language.zh-Hans")` → `"Chinese (Simplified)"` in English UI, `"简体中文"` in Chinese UI). Live verification on build 130 with either `appLanguage = zh-Hans` or per-app `AppleLanguages = (zh-Hans-CN)` confirmed Chinese UI resolves `"language.zh-Hans"` to `"简体中文"`.
  2. **Fallback hardening gap in `Language.swift`**: `Language.name` called `L("language.\(code)")`, which falls back to `en.lproj` before anything else and returns raw BCP-47 codes for uncataloged/regional identifiers (e.g., `"sv"`, `"zh-Hans-CN"`), and lacked a testable UI-language parameterized API.
- **Fix**:
  - Added `Language.localizedName(in language: String = L10n.language)` in `Sources/Shocrot/Translate/Language.swift` and routed `Language.name` through it: looks up `L10n.table(language)["language.\(code)"]` first, then `Locale(identifier: language).localizedString(forIdentifier: code)` (so uncataloged or regional codes localize into the active UI language rather than leaking English or raw tags), then the fallback table and raw code; `englishName` remains English for LLM system prompts.
  - Added `@Suite("Localized language names")` (4 tests) in `Tests/ShocrotTests/LocalizationTests.swift` verifying all 20 `Language.all` names in `zh-Hans` (`简体中文`, `英语`, `日语`, …) vs `en` (`Chinese (Simplified)`, `English`, `Japanese`, …), uncataloged/regional codes, invalid code fallback, and `Language.name == localizedName(in: L10n.language)`.
- **Live Verification & Screenshots**:
  - Chinese UI (`appLanguage = zh-Hans` and per-app `AppleLanguages = (zh-Hans-CN)`): displays **`简体中文`** (`r2_popover_textedit_dark.png`, `r2_popover_textedit_light.png`, `r2_popover_safari_dark.png`, `r2_popover_safari_light.png`).
  - English UI (restored default `en-US` preferences): displays **`Chinese (Simplified)`** (`r2_popover_en_ui.png`).
